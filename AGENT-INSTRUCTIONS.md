# Implement Gmail-compatible message search

Use https://github.com/mrjf/gpuf as the reference implementation. Integrate it into the current project and run it. Start by cloning the repository, reading README.md, and running `bun install --frozen-lockfile`, `bun test src`, and `bun run demo` in the clone. The example uses a synthetic RFC 822 email and works offline after dependency installation.

1. Inspect the project's language, mail source, account identity, storage, search entry point, and existing authorization. In TypeScript, reuse the modules in `src/` directly. In another language, port the row builder, query compiler, and search planner together. Use the same mail input in both implementations and compare their message rows, chunk IDs and text, emitted predicates, page boundaries, and ordered result IDs. Use idiomatic libraries for MIME, PDF, Office XML, storage, and HTTP.
2. Start with the reference `MESSAGE_SCHEMA` and `CHUNK_SCHEMA` in `src/gmail-index.ts`. Use the two account- and generation-specific namespaces in `src/turbopuffer.ts`. Obtain the target region, server-side turbopuffer key, and stable mailbox identity from project configuration. Connect a Gmail source through the project's read-only OAuth integration, or adapt another authorized source to the `GmailMessage` shape. Keep original MIME and sync checkpoints in durable storage.
3. Implement replayable backfill, updates, and deletion as described in the README. Use `indexMessage` for raw messages. Persist previous chunk IDs so changed content can remove obsolete passages. Apply label and source-state patches to both namespaces. Use `src/gmail-query-state.ts` for Gmail-only memberships. Only advertise capabilities collected for the active mailbox and generation.
4. Route Gmail expressions to `searchMailIndex({query, mode: 'gmail'}, context, namespaces, queryTransport)`. Expose ranked modes separately. Preserve the reference token boundaries, dates, default visibility, explicit predicates, cursor behavior, and result limits. Use the reference ranking weights as the baseline for evaluating custom rankers. Translate SDK parameter names only at the HTTP boundary. Keep cross-language ports testable against the TypeScript implementation.
5. Run the synthetic tests and the end-to-end fixture with `bun run examples/demo.ts --live` against the configured region when credentials are available. That command writes two new synthetic namespaces and leaves them for inspection. Compare a private fixture corpus against Gmail with the procedure in the README. Report exact-set differences, ingestion coverage, sample size, and errors. Keep mailbox contents and credentials out of commits and reports.

## Extend the semantic search API

Design the ranked API around what people want to find in your application. You can add endpoints, request options, response fields, ranking strategies, and indexes. For example, a receipt search could accept `{"query":"from:shop@example.org running shoes","ranking":"receipts","includePassages":true}` and return each matching message with the passage that mentions the purchase. The sender is a hard filter. “Running shoes” is the text to rank. The new options in this example belong to your application API.

- **Choose the retrieval strategy.** Use any turbopuffer feature that fits the task and is available for your account and region. Examples include field-weighted BM25 for product names, fuzzy matching for typos, dense passage vectors for paraphrases, or sparse vectors for a domain-specific model. Batch branches that query the same namespace with multi-query, then fuse their ranked lists. If a strategy needs a new indexed attribute, populate it in a new generation before routing traffic to it. [Query API](https://turbopuffer.com/docs/query) · [Hybrid search](https://turbopuffer.com/docs/hybrid)
- **Implement a custom reranker after candidate fusion.** In `src/gmail-search.ts`, the extension point is between `fuse(...)` and the final result slice. The reference uses native `rerank_by` on up to 30 candidates. You can select a supported native model or implement an application-side function such as `rerank(query, candidates) → ordered message IDs`. For receipts, score the query against each candidate’s matched passage and bounded `rerank_text`, then break ties by the fused order. A cross-encoder or a scoring function using your own metadata can implement the same interface. [Native reranking](https://turbopuffer.com/docs/reranking)
- **Keep Gmail predicates binding.** Run every branch within the authenticated mailbox. Check passage hits against the complete predicate on their parent messages and deduplicate by message ID before reranking. Accept only IDs from that eligible candidate set. Strict Gmail mode keeps its chronological cursor, while ranked responses report bounded results.
- **Evaluate the extension against the baseline.** Use held-out queries with known relevant messages and compare top-three usefulness or reciprocal rank. Include a fixture where the strongest semantic match has the wrong sender, plus one where several passages belong to the same message. Check that the new API returns the intended order, unique eligible IDs, and the right passage for each hit.

Deliver working changes in the project's normal indexing and search paths, the focused test results, and a short list of any unsupported source metadata, extraction formats, or unverified live steps.
